## User Scenarios & Testing *(mandatory)*

### User Story 1 - 이메일로 가입하고 인증한 뒤 글을 쓸 수 있다 (Priority: P1)

방문자가 이메일·블로그 주소·비밀번호·닉네임을 입력하고 필수 약관 2개에 동의해 가입한다. 가입 직후 인증 메일이 발송되고, 메일 링크를 누르면 인증이 끝나 글쓰기·댓글·사진 업로드를 할 수 있다. 인증 전에도 로그인은 되지만 쓰기 행동은 막히고 "인증 메일 다시 보내기" 안내를 받는다.

**Why this priority**: 이메일 가입은 공통 필수(Tier A, C-AUTH-1)이며, 모든 쓰기 기능의 전제다. 이것만 있어도 회원이 글을 쓸 수 있는 최소 서비스가 된다.

**Independent Test**: 새 이메일로 가입 → 인증 전 글쓰기 시도(거부 확인) → 인증 링크 클릭 → 글쓰기 시도(허용 확인)로 독립 검증할 수 있다.

**Acceptance Scenarios**:

1. **Given** 가입되지 않은 이메일, **When** 규칙에 맞는 비밀번호·블로그 주소·닉네임과 필수 약관 2개 동의로 가입하면, **Then** 계정이 미인증 상태로 만들어지고 24시간 유효한 인증 메일이 발송되며 약관 동의 시각이 기록된다.
2. **Given** 미인증 회원, **When** 글쓰기·댓글·사진 업로드·좋아요·신고를 요청하면, **Then** 계정 상태 거부(이메일 미인증 이유 포함)로 거부되고 "인증 메일 다시 보내기" 안내가 보인다.
3. **Given** 미인증 회원이 받은 유효한 인증 링크, **When** 링크를 누르면, **Then** 인증 시각이 기록되고 "인증이 완료됐어요"가 보이며 이후 글쓰기가 허용된다.
4. **Given** 이미 한 번 사용했거나 24시간이 지난 인증 링크, **When** 다시 누르면, **Then** "링크가 만료됐어요. [인증 메일 다시 보내기]"가 보이고 인증되지 않는다.
5. **Given** 이미 이메일 가입된 주소, **When** 같은 이메일(대소문자·앞뒤 공백만 다름 포함)로 다시 가입하면, **Then** 새 계정이 생기지 않고 "이미 가입된 이메일이에요. [로그인] [비밀번호 찾기]"가 보인다.
6. **Given** 비밀번호가 8자 미만, 16자 초과, 또는 영문·숫자·특수문자 중 하나라도 없음, **When** 가입하면, **Then** 가입이 거부된다.
7. **Given** 미인증 회원, **When** 인증 메일 재발송을 1분 안에 두 번 요청하거나 하루 10번을 넘겨 요청하면, **Then** 초과 요청은 발송되지 않는다. 새 메일이 발송되면 이전 링크는 무효가 된다.

### User Story 2 - 이메일로 로그인·로그아웃한다 (Priority: P1)

가입한 회원이 이메일과 비밀번호로 로그인해 14일 동안 로그인 상태를 유지하고, 로그아웃하면 서버의 로그인 상태와 브라우저에 남은 임시 작성 데이터가 모두 지워진다. 실패 메시지와 잠금으로 계정을 보호한다.

**Why this priority**: 로그인·로그아웃은 C-AUTH-1의 핵심이며 공용 PC 안전(로그아웃 시 임시 데이터 삭제) 결정과 직결된다.

**Independent Test**: 로그인 → 보던 페이지로 이동 확인 → 로그아웃 → 쓰기 요청 거부 및 브라우저 임시 데이터 삭제 확인; 틀린 비밀번호 5회 → 잠금 확인.

**Acceptance Scenarios**:

1. **Given** 가입된 회원, **When** 올바른 이메일·비밀번호로 로그인하면, **Then** 로그인되고 로그인 전에 보던 우리 사이트 안의 페이지로 이동하며 마지막 로그인 시각이 기록된다.
2. **Given** 로그인 화면, **When** 없는 이메일 또는 틀린 비밀번호로 로그인하면, **Then** 두 경우 모두 "이메일 또는 비밀번호가 올바르지 않아요"라는 같은 메시지가 보인다.
3. **Given** 같은 계정에 대해 5회 연속 로그인 실패, **When** 15분 이내에 다시 로그인하면, **Then** 올바른 비밀번호여도 로그인되지 않고 "잠시 후 다시 시도해 주세요(약 15분)"가 보인다.
4. **Given** 로그인한 회원, **When** 로그아웃하면, **Then** 서버의 로그인 상태가 삭제되고, 그 회원의 브라우저 임시 작성 데이터와 백업이 모두 삭제되며 홈으로 이동한다.
5. **Given** 로그아웃한 브라우저, **When** 글쓰기 등 쓰기 요청을 보내면, **Then** 로그인 필요로 거부된다.
6. **Given** 로그인 후 이동할 주소로 외부 사이트 주소가 주어짐, **When** 로그인하면, **Then** 외부로 이동하지 않는다.
7. **Given** 마지막 활동 후 14일이 지나지 않은 회원, **When** 다시 접속하면, **Then** 로그인 상태가 유지된다. 14일 동안 활동이 없으면 로그인이 풀린다.

### User Story 3 - Google·GitHub 계정으로 가입·로그인한다 (Priority: P1)

방문자가 [Google로 계속하기]/[GitHub로 계속하기]를 누른다. 처음이면 가입 마무리 화면에서 닉네임·블로그 주소·약관 동의를 마친 뒤 계정이 만들어지고, 이미 연결된 계정이면 바로 로그인된다. 같은 이메일이라도 로그인 수단이 다르면 별도 계정이다.

**Why this priority**: 결정 기록(2026-10-02)에서 이메일 + Google + GitHub이 공통 범위로 확정됐다(C-AUTH-1).

**Independent Test**: 같은 Google 계정으로 두 번 로그인해 계정이 1개임을 확인하고, 같은 이메일의 이메일 가입 계정과 Google 계정이 서로 다른 계정임을 확인한다.

**Acceptance Scenarios**:

1. **Given** 처음 로그인하는 Google 계정, **When** 인증을 마치면, **Then** 계정은 아직 만들어지지 않고 가입 마무리 화면(닉네임 미리 채움, `go-` 고정 접두어가 붙은 블로그 주소, 약관 동의)이 보인다.
2. **Given** 가입 마무리 화면, **When** 닉네임·블로그 주소·필수 약관 동의로 완료하면, **Then** 계정이 만들어지고 가입 시각으로 이메일 인증이 완료된 상태가 된다.
3. **Given** 가입 마무리 화면에서 10분 동안 완료하지 않음, **When** 이후 완료를 시도하면, **Then** 소셜 인증 정보가 사라져 다시 소셜 인증부터 해야 한다.
4. **Given** 이미 가입된 Google 계정, **When** 다시 로그인하면, **Then** 새 계정 없이 기존 계정으로 로그인된다. 그 Google 계정의 이메일이 바뀌었어도 같은 계정이다.
5. **Given** `a@x.com`으로 이메일 가입한 계정이 있음, **When** 이메일이 같은 Google 계정으로 처음 로그인하면, **Then** 기존 계정과 합쳐지지 않고 별도의 새 계정 가입 흐름으로 간다. 가입 마무리 화면에는 "이 이메일로 가입한 계정이 이미 있어요. [기존 계정으로 로그인] [새 계정 만들기]" 안내가 함께 보이고, [기존 계정으로 로그인]을 누르면 아무 계정도 만들어지지 않은 채 로그인 화면으로 이동한다. (clarify 2026-10-07, 사용자 확정 2026-10-07)
6. **Given** 인증된 대표 이메일이 없는 GitHub 계정, **When** 가입 마무리 화면에 들어오면, **Then** 이메일을 입력받아 이메일 가입과 같은 방식으로 인증한다.

### User Story 4 - 비밀번호를 잊었을 때 재설정한다 (Priority: P2)

이메일 가입 회원이 비밀번호 찾기에서 이메일을 입력하면 30분 동안 한 번 쓸 수 있는 재설정 링크를 받는다. 새 비밀번호를 저장하면 그 계정의 모든 기기에서 로그아웃된다. 화면만으로는 가입 여부를 알 수 없다.

**Why this priority**: 공통 범위(L-4)이지만 가입·로그인이 먼저 있어야 의미가 있다.

**Independent Test**: 가입된 이메일과 가입되지 않은 이메일로 각각 요청해 화면 문구가 같음을 확인 → 재설정 링크로 비밀번호 변경 → 다른 기기 세션 종료 확인.

**Acceptance Scenarios**:

1. **Given** 아무 이메일, **When** 비밀번호 찾기를 요청하면, **Then** 가입 여부와 상관없이 항상 "가입된 이메일이면 안내 메일을 보냈어요"가 보인다.
2. **Given** 이메일 가입 계정이 있는 이메일, **When** 비밀번호 찾기를 요청하면, **Then** 그 이메일로 30분 유효·1회용 재설정 링크가 발송되고, 같은 이메일의 Google·GitHub 계정이 있으면 "그 계정은 Google(GitHub)로 로그인하세요" 안내가 함께 담긴다.
3. **Given** 소셜 계정만 있는 이메일, **When** 비밀번호 찾기를 요청하면, **Then** 재설정 링크 없이 "이 이메일은 Google로 가입되어 비밀번호가 없어요" 안내 메일만 간다.
4. **Given** 유효한 재설정 링크, **When** 규칙에 맞는 새 비밀번호를 저장하면, **Then** 비밀번호가 바뀌고 그 계정의 모든 기기 로그인이 끊긴다.
5. **Given** 이미 쓴 링크 또는 30분이 지난 링크, **When** 다시 사용하면, **Then** 비밀번호를 바꿀 수 없다.
6. **Given** 규칙에 맞지 않는 새 비밀번호, **When** 재설정하면, **Then** 거부된다.

### Edge Cases

- 같은 이메일로 이메일 가입을 동시에 두 번 요청 → 계정은 하나만 생긴다.
- 같은 소셜 계정으로 가입 마무리를 동시에 두 번 완료 → 계정은 하나만 생긴다.
- 이메일 앞부분이 들어간 비밀번호(`kim755030@…`의 `kim755030` 포함) 또는 흔한 비밀번호 목록(`Password1!`, `Qwer1234!` 등) → 규칙을 만족해도 거부된다.
- 비밀번호에 공백·한글 포함 → 거부된다. 허용 특수문자는 원문 §4 목록에 한정한다.
- 17자 이상 비밀번호(비밀번호 관리자가 만든 긴 비밀번호) → 거부되며, 안내 문구에 "최대 16자"가 분명히 적혀 있다.
- 같은 IP에서 1분에 20회를 넘는 로그인 시도 → 차단된다.
- 비밀번호 찾기: 같은 이메일 1분에 1번·하루 10번, 같은 IP 1시간에 20번을 넘으면 발송하지 않는다(화면 문구는 동일).
- 인증 메일 재발송 후 이전 링크 클릭 → 무효.
- Google 이메일이 인증되지 않은(`email_verified`가 아닌) 경우 → 그 이메일은 쓰지 않는다.
- GitHub 로그인 이름이 바뀜 → 고유 숫자 ID로 식별하므로 같은 계정이다.
- 정지된 회원의 로그인 → 로그인되지 않고 "정지된 계정이에요 (~기한, 사유)"가 보인다 (42 P-7).
- 탈퇴 유예 회원의 로그인 → 복구 화면만 보인다 (42 P-12, 회원 탈퇴 기능과 연계).
- 정지 회원도 비밀번호 재설정(로그인 전 기능)은 할 수 있다.
- 로그인 직후 이전 세션 식별자는 재사용되지 않는다(세션 고정 방지).

## Requirements *(mandatory)*

### Functional Requirements

**계정과 로그인 수단**

- **FR-001**: System MUST 로그인 수단으로 이메일 가입, Google, GitHub 세 가지를 제공해야 한다. 네이버 등 다른 수단은 이번 범위에서 제외한다. (C-AUTH-1)
- **FR-002**: System MUST 같은 로그인 수단(같은 이메일 가입, 같은 소셜 계정)으로는 계정을 두 개 만들지 않아야 하며, 동시 요청에서도 이를 보장해야 한다. (C-AUTH-1)
- **FR-003**: System MUST 로그인 수단이 다르면 이메일이 같아도 별도 계정으로 다뤄야 하며, 계정을 자동으로 합치거나 다른 로그인 수단을 연결하는 기능을 제공하지 않아야 한다. 계정 하나에는 로그인 수단이 하나다. (C-AUTH-1)
- **FR-004**: System MUST 이메일 가입 계정은 소문자로 바꾸고 앞뒤 공백을 지운 이메일로, 소셜 계정은 이메일이 아닌 소셜 서비스의 고유 사용자 ID(Google 고유 ID, GitHub 숫자 ID)로 식별해야 한다. 바뀔 수 있는 로그인 이름은 식별에 쓰지 않는다.

**이메일 가입·인증**

- **FR-005**: System MUST 이메일 가입 시 이메일(일반 이메일 형식, 최대 254자), 블로그 주소, 비밀번호, 비밀번호 확인, 닉네임, 필수 약관 2개(이용약관, 개인정보 수집·이용) 동의를 받아야 한다. 블로그 주소·닉네임 규칙은 002 기능을 따른다. (C-AUTH-1)
- **FR-006**: System MUST 약관 2개 각각의 동의 시각을 저장해야 하며, 둘 중 하나라도 동의하지 않으면 가입을 거부해야 한다.
- **FR-007**: System MUST 이미 이메일 가입된 주소로 가입을 시도하면 "이미 가입된 이메일이에요. [로그인] [비밀번호 찾기]"를 안내하고 계정을 만들지 않아야 한다.
- **FR-008**: System MUST 이메일 가입 직후 인증 메일을 보내야 하며, 인증 링크는 24시간 유효하고 한 번만 쓸 수 있어야 한다. 인증 링크는 추측할 수 없는 충분히 긴 난수여야 한다.
- **FR-009**: System MUST 인증 메일 재발송을 회원당 1분에 1번, 하루 10번으로 제한하고, 새 메일을 보내면 이전 링크를 무효로 해야 한다.
- **FR-010**: System MUST 만료되었거나 이미 사용된 인증 링크에는 "링크가 만료됐어요. [인증 메일 다시 보내기]"를 보여줘야 한다.
- **FR-011**: System MUST 이메일 인증 전 회원의 로그인은 허용하되, 글쓰기·댓글·사진 업로드(및 42 권한 매트릭스에 따른 좋아요·신고)는 계정 상태 거부(403, 이유 `EMAIL_NOT_VERIFIED`)로 막고 인증 메일 재발송 방법을 안내해야 한다. 인증 전 회원의 자기 글·댓글 삭제·복구는 허용한다. (C-AUTH-1, C-OWN-1)

**비밀번호**

- **FR-012**: System MUST 비밀번호를 8~16자, 영문(대소문자 중) 1개 이상·숫자 1개 이상·특수문자 1개 이상으로 제한해야 하며, 쓸 수 있는 문자는 영문·숫자·지정된 특수문자뿐이다(공백·한글 불가). 가입·재설정·변경 모두 같은 규칙을 쓴다. (C-AUTH-1)
- **FR-013**: System MUST 이메일 `@` 앞부분이 들어간 비밀번호와 흔한 비밀번호 목록에 있는 비밀번호를 거부해야 한다.
- **FR-014**: System MUST 비밀번호를 되돌릴 수 없는 방식으로만 저장하고, 비밀번호 원문·인증 토큰을 저장하거나 로그에 남기지 않아야 한다.
- **FR-015**: System MUST 비밀번호 입력 중 규칙별 충족 여부를 글자와 기호(✓)로 보여줘야 하며 색만으로 구분하지 않아야 하고, "최대 16자" 안내를 분명히 보여줘야 한다.

**비밀번호 재설정**

- **FR-016**: System MUST 비밀번호 찾기 요청에 가입 여부와 상관없이 항상 "가입된 이메일이면 안내 메일을 보냈어요"만 보여줘야 한다. (C-AUTH-1 기준 7)
- **FR-017**: System MUST 이메일 가입 계정이 있으면 30분 유효·1회용 재설정 링크를 그 이메일로 보내고, 같은 이메일의 소셜 계정이 있으면 그 수단으로 로그인하라는 안내를 덧붙여야 한다. 소셜 계정만 있으면 "비밀번호가 없어요" 안내만 보내야 한다.
- **FR-018**: System MUST 비밀번호 찾기 요청을 같은 이메일 1분에 1번·하루 10번, 같은 IP 1시간에 20번으로 제한해야 한다.
- **FR-019**: System MUST 재설정으로 새 비밀번호를 저장하면 그 계정의 모든 로그인 세션을 끊어야 한다(모든 기기 로그아웃). (C-AUTH-1 기준 5)

**소셜 로그인**

- **FR-020**: System MUST 소셜 로그인 과정에서 요청 위조 방지를 위한 상태 값을 검증해야 한다.
- **FR-021**: System MUST 처음 소셜 로그인한 사용자를 반드시 가입 마무리 화면(닉네임 필수·소셜 이름을 정리해 미리 채움, 고정 접두어가 붙은 블로그 주소, 약관 동의)으로 보내야 하며, 마무리 전에는 계정을 만들지 않고 소셜 인증 정보는 10분만 보관해야 한다.
- **FR-022**: System MUST 소셜 가입 계정은 가입 시각을 이메일 인증 시각으로 기록해야 한다. Google은 인증된 이메일만 쓰고, GitHub은 인증된 대표 이메일을 쓰며 없으면 마무리 화면에서 이메일을 받아 FR-008과 같은 방식으로 인증해야 한다.
- **FR-023**: System MUST 가입 마무리 화면에서 "프로필 사진 사용"(기본 체크)을 제공하고, 체크된 경우 계정 생성 직후 소셜 프로필 사진의 복사본을 프로필 이미지로 연결해야 한다(세부는 003 기능).
- **FR-033**: System MUST 처음 소셜 로그인한 사용자의 인증된 이메일과 같은 이메일을 가진 다른 로그인 수단의 계정이 있으면, 가입 마무리 화면에 "이 이메일로 가입한 계정이 이미 있어요. [기존 계정으로 로그인] [새 계정 만들기]" 안내를 보여줘야 한다. 계정을 합치거나 연결하지 않으며, 인증되지 않은 이메일로는 안내하지 않는다. (07 §10 F-1, clarify 2026-10-07, 사용자 확정 2026-10-07)

**로그인 유지와 보안**

- **FR-024**: System MUST 로그인 상태를 마지막 활동 시점부터 14일 동안 유지해야 하며, 서버를 여러 대로 늘려도 유지되어야 한다.
- **FR-025**: System MUST 같은 계정 5회 연속 로그인 실패 시 15분 동안 로그인을 잠그고 "잠시 후 다시 시도해 주세요(약 15분)"를 보여줘야 하며, 같은 IP의 로그인 시도는 1분에 20회로 제한해야 한다. (C-AUTH-1 기준 6)
- **FR-026**: System MUST 로그인 실패 시 이메일과 비밀번호 중 어느 쪽이 틀렸는지 알려주지 않는 동일 메시지("이메일 또는 비밀번호가 올바르지 않아요")를 보여줘야 한다. (C-AUTH-1 기준 7)
- **FR-027**: System MUST 로그인 후 보던 페이지로 돌려보내되 우리 사이트 안의 상대 경로만 허용해야 한다.
- **FR-028**: System MUST 로그인할 때 세션 식별자를 새로 발급하고, 로그인 쿠키는 스크립트로 읽을 수 없고 보안 연결로만 전송되며 다른 사이트 요청에 실리지 않게(Lax) 설정해야 하며, 요청 위조(CSRF) 방어를 유지해야 한다.
- **FR-029**: System MUST 로그인 성공 시 마지막 로그인 시각을 기록해야 한다.
- **FR-030**: System MUST 정지된 회원의 로그인을 거부하고 정지 기한·사유를 안내해야 하며, 탈퇴 유예 회원이 로그인하면 복구 화면만 보여줘야 한다. (42 P-7, P-12)

**로그아웃**

- **FR-031**: System MUST 로그아웃 시 서버의 로그인 상태를 삭제하고, 그 사용자의 브라우저 임시 작성 데이터와 백업을 모두 삭제한 뒤 홈으로 이동해야 한다. (C-AUTH-1 기준 2, 공용 PC 결정)
- **FR-032**: System MUST 로그아웃 후의 쓰기 요청을 로그인 필요(401, 서버 렌더링 화면은 로그인 화면으로 이동)로 거부해야 한다. (C-AUTH-1, 42 §4)

### Key Entities *(include if feature involves data)*

- **회원(Member)**: 블로그 하나를 가진 사람. 블로그 주소, 닉네임, 약관 동의 시각(이용약관·개인정보), 계정 상태(활성·정지·탈퇴 유예)를 가진다.
- **로그인 수단(Auth Identity)**: 회원 한 명에 정확히 하나. 수단 종류(이메일·Google·GitHub), 수단 안에서의 고유 식별값(이메일 가입은 소문자 이메일, 소셜은 고유 ID), 이메일, 이메일 인증 시각, 비밀번호(이메일 가입만, 되돌릴 수 없는 형태), 마지막 로그인 시각. (수단 종류, 식별값) 조합은 유일하다.
- **인증 링크·재설정 링크**: 회원을 가리키는 1회용 난수 토큰. 유효 시간(인증 24시간, 재설정 30분)이 지나거나 사용하면 사라진다.
- **로그인 세션**: 회원의 로그인 상태. 마지막 활동부터 14일 유지. 재설정·정지 시 회원의 모든 세션이 삭제된다.
- **요청 횟수 기록**: 로그인 실패 횟수, 재발송·재설정 요청 횟수. 정해진 시간 창이 지나면 사라진다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 같은 이메일로 이메일 가입을 동시에 20번 요청해도, 같은 소셜 계정으로 가입 마무리를 동시에 20번 완료해도 계정은 정확히 1개만 생긴다.
- **SC-002**: 미인증 회원의 글쓰기·댓글·사진 업로드 요청은 100% 거부되고, 그동안 어떤 데이터도 생기지 않는다.
- **SC-003**: 규칙 위반 비밀번호 유형(8자 미만, 16자 초과, 영문·숫자·특수문자 각 누락, 이메일 앞부분 포함, 흔한 비밀번호) 각각에 대해 가입·재설정이 100% 거부된다.
- **SC-004**: 비밀번호 재설정 후 그 계정의 다른 모든 기기 세션이 즉시(다음 요청에서) 로그인 필요 상태가 된다.
- **SC-005**: 5회 연속 실패 후 15분 동안 올바른 비밀번호로도 로그인할 수 없고, 15분이 지나면 로그인할 수 있다.
- **SC-006**: 가입된 이메일과 가입되지 않은 이메일에 대해 로그인 실패 화면·비밀번호 찾기 화면의 응답 문구가 글자 하나까지 같다.
- **SC-007**: 인증·재설정 링크는 두 번째 사용과 만료 후 사용이 100% 거부된다.
- **SC-008**: 로그아웃 후 브라우저에 그 사용자의 임시 작성 데이터가 하나도 남지 않는다.
- **SC-009**: 신규 방문자가 이메일 가입 화면에서 가입 완료까지 3분 이내에 마칠 수 있다.

## Assumptions

- Tier A(공통 필수) 기능이다: C-AUTH-1. 결정 기록 2026-10-02의 "로그인 방식", "같은 이메일 다른 로그인 수단 = 별도 계정", "이메일 인증", "비밀번호", "로그인 유지·보안", "약관 동의", "공용 PC" 결정을 따른다.
- C-AUTH-1 완료 기준은 "같은 사람이 계정 두 개가 되지 않는다"에서 "같은 로그인 수단으로는 계정 1개"로 변경된 기준을 쓴다.
- 인증 전 회원이 막히는 행동은 07 원문(글쓰기·댓글·사진)에 42 권한 매트릭스(2026-10-03)가 좋아요·신고를 더한 범위다.
- 화면 구성(서버 렌더링+세션 / REST+토큰)은 팀원마다 고를 수 있다(01 Q2). 토큰 방식이면 갱신 토큰을 서버 쪽에 저장하고 재발급마다 교체해 같은 효과(로그아웃·재설정 시 무효화)를 낸다.
- 수치(링크 유효 시간, 재발송·재설정 제한, 잠금 횟수·시간, IP 제한, 로그인 유지 기간)는 설정값으로 둔다.
- 운영 환경의 메일 발송 방식은 환경 확인 후 정한다(L-9). 명세상 요구는 "메일이 해당 이메일 주인에게 전달된다"뿐이다.
- 설정 화면의 "모든 기기에서 로그아웃" 버튼은 개인 확장이다(재설정 시 자동 실행만 공통).
- 비밀번호 변경(로그인 상태)은 003-profile 기능에서 다룬다. 블로그 주소·닉네임 규칙은 002 기능에서 다룬다.
- 정지·탈퇴 유예 상태 자체의 관리(정지 처리, 탈퇴·복구)는 각각 신고·숨김(43), 회원 탈퇴(13·44) 기능의 범위이고, 이 기능은 로그인 시점의 처리만 맡는다.
- 소셜 첫 로그인 시 같은 이메일의 다른 수단 계정을 안내하는 기능(07 §10 F-1)은 공통으로 넣는다: 가입 마무리 화면에서 "기존 계정으로 로그인 / 새 계정 만들기"를 안내하되 계정은 합치지 않는다 (FR-033). (clarify 2026-10-07, 사용자 확정 2026-10-07)
