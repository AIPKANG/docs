# 성능 확인 (2026-10-08)

**환경**: MacBook Air(Apple Silicon), 앱은 로컬 실행(개발 프로필), PostgreSQL 18·Redis는 Docker. 운영 서버(2 vCPU·4GB)에서는 더 느릴 수 있으니 배포 뒤 같은 방법으로 다시 잰다.

**데이터**: 회원 1,000, 글 100,000(공개 92%·비공개 5%·임시 3%, 본문 120~320단어), 태그 500(글마다 3개), 팔로우 2만, 좋아요 약 30만, 댓글 약 19만. DB 690MB. 최근 7일 공개 글 1,700(트렌딩 대상).

**재는 법**: 주소마다 5번 예열 뒤 30번 연속 요청, 중앙값(p50)과 95번째(p95), 단위 ms. 검색은 요청 제한을 피하려고 요청마다 다른 방문자로.

| 화면·API | p50 | p95 | 목표(명세) |
|---|---:|---:|---|
| 홈 첫 화면 `/` | 10 | 15 | 300 |
| 목록 API 다음 쪽 | 2 | 5 | 300 |
| 개인 블로그 `/@user0007` | 20 | 33 | 300 |
| 태그별 목록 `/tags/tag42` | 16 | 21 | 300 |
| 글 상세 | 13 | 20 | 300 |
| 트렌딩 API / 화면 | 7 / 14 | 8 / 20 | 200 |
| 팔로잉 피드(로그인, 50명 팔로우) | 14 | 21 | 300 |
| 검색 흔한 단어 "스프링" | 7 | 13 | 500 |
| 검색 두 단어 "도커 캐시" | 8 | 10 | 500 |
| 검색 드문 단어(최근창에 없음 → 인덱스 단계) | 80 | 83 | 500 |
| 검색 결과 없는 단어 | 86 | 94 | 500 |
| 검색 최신순 / 사람 검색 | 5 / 5 | 5 / 5 | 500 |

**동시 접속**: 20명이 15초 동안 홈·블로그·상세·태그·트렌딩·검색을 섞어 요청 → 12,137건(초당 약 800), p50 22ms, p95 49ms, 오류 0.

**결론**: 모든 항목이 목표의 1/3 아래라 이번에는 고칠 곳이 없다. 가장 느린 것은 드문 단어 검색(최근 글 3,000개 안에 없어 트라이그램 인덱스로 다시 찾는 경우)으로 약 90ms. 글이 더 많아져 느려지면 `blog.search.recent-window`를 줄이거나(33 §8) 본문 인덱스를 점검한다.
