## User Scenarios & Testing *(mandatory)*

### User Story 1 - 에디터에 사진을 붙여 넣어 바로 올리기 (Priority: P1)

작성자는 에디터에 사진을 붙여 넣거나 끌어다 놓는다. 브라우저가 사진을 줄이고 촬영 위치(EXIF)를 지운 뒤 목록 카드용 썸네일까지 만들어 저장소에 바로 올리고, 본문에는 사진 주소만 들어간다. 임시저장 흐름과는 분리되어 글 저장이 무거워지지 않는다.

**Why this priority**: C-IMG-1의 핵심 흐름이다. 이것만으로도 사진이 든 글을 쓸 수 있다.

**Independent Test**: 인증된 회원이 jpg 사진 하나를 에디터에 넣어 업로드가 끝난 뒤 본문에 우리 저장소 주소가 들어가고, 원본·썸네일 파일이 모두 저장소에 있으며, 원본에서 위치 정보가 제거됐는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 이메일 인증을 마친 회원, **When** 5MB jpg 사진을 에디터에 붙여 넣으면, **Then** 브라우저가 긴 변 최대 1920px·WebP(품질 0.8)로 바꾸고 위치 정보를 지운 원본과, 가로 최대 640px WebP 썸네일을 올리며, 본문에는 우리 저장소 주소만 들어간다.
2. **Given** 업로드 승인 요청, **When** 형식·크기·요청 횟수 검사를 통과하면, **Then** 원본·썸네일용 업로드 주소 2개가 5분 동안만 유효하게 발급되고, 사진 데이터는 서비스 서버를 거치지 않고 저장소로 직접 올라간다.
3. **Given** 업로드가 끝난 사진, **When** 완료를 알리면, **Then** 서버가 두 파일의 존재·실제 크기·파일 앞부분의 실제 형식·해상도를 다시 검사하고, 통과하면 주소를 돌려주며 실패하면 파일을 지운다.
4. **Given** 사진이 든 글, **When** 발행하면, **Then** 본문의 첫 번째 업로드 사진의 썸네일이 목록 카드 썸네일로 지정되고, 본문에 쓰인 사진은 그 글에 연결된 것으로 기록된다.
5. **Given** 업로드된 사진, **When** 저장 이름을 보면, **Then** 서버가 만든 추측할 수 없는 이름이고, 사용자가 올린 원래 파일 이름은 주소나 화면 어디에도 나오지 않는다.

### User Story 2 - 위험하거나 규칙에 맞지 않는 파일 거부 (Priority: P1)

시스템은 jpg·png·gif·webp가 아닌 파일, 10MB를 넘는 파일, 확장자를 위장한 파일, 손상된 파일, 지나치게 큰 해상도의 파일을 거부한다. 브라우저 검사를 우회해도 서버가 다시 거부한다.

**Why this priority**: C-IMG-1 공통 완료 기준(형식·크기·위장 거부)이며 저장소 악용을 막는다.

**Independent Test**: 형식 위장 파일(실행 파일을 .jpg로), 11MB 파일, 1만 px을 넘는 이미지, 썸네일 규격 위반 파일을 업로드해 모두 거부되고 저장소에서 파일이 지워지는지 확인한다.

**Acceptance Scenarios**:

1. **Given** jpg·png·gif·webp가 아닌 형식, **When** 업로드 승인을 요청하면, **Then** 거부된다.
2. **Given** 10MB를 넘는 파일, **When** 업로드 승인을 요청하면, **Then** 거부된다.
3. **Given** 확장자·신고 형식은 jpg인데 실제 내용은 다른 형식인 파일, **When** 완료를 알리면, **Then** 거부되고 저장소에서 파일이 지워진다.
4. **Given** 신고한 크기보다 실제 크기가 큰 파일, **When** 완료를 알리면, **Then** 거부되고 파일이 지워진다.
5. **Given** 썸네일이 가로 640px 또는 1MB를 넘음, **When** 완료를 알리면, **Then** 거부되고 파일이 지워진다.
6. **Given** 비회원, **When** 업로드를 요청하면, **Then** 로그인 필요(401)로 거부된다.
7. **Given** 이메일 인증 전 회원, **When** 업로드를 요청하면, **Then** 403과 "인증 메일 다시 보내기" 안내로 거부된다.
8. **Given** 1분 안에 20장을 넘게 요청한 회원, **When** 21번째를 요청하면, **Then** 요청 제한으로 거부된다.

### User Story 3 - 사용자별 저장 공간과 하루 업로드 한도 (Priority: P2)

한 사람이 저장소를 채우지 못하도록 회원마다 1GB 저장 공간과 하루 200장 한도가 있다. 회원은 설정 화면에서 사용량을 확인하고, 한도에 가까워지거나 넘으면 에디터에서 안내를 받는다.

**Why this priority**: 운영 안정성을 위한 보호 장치다. 1차 흐름(Story 1·2)이 먼저 동작해야 의미가 있다.

**Independent Test**: 사용량이 한도 직전인 회원으로 동시에 업로드 승인 10건을 보내 합계가 1GB를 넘지 않는지, 하루 201번째 요청이 거부되는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 현재 사용량 + 이번에 올릴 크기(원본 + 썸네일)가 1GB를 넘는 회원, **When** 업로드 승인을 요청하면, **Then** 저장 공간 초과(409)로 거부되고 에디터에 "사진 저장 공간(1GB)을 다 썼어요. 쓰지 않는 사진이 든 글을 지우면 7일 뒤 공간이 돌아와요"가 보인다.
2. **Given** 한도 직전의 회원, **When** 업로드 승인 10건을 동시에 보내면, **Then** 허용된 요청의 합계가 1GB를 넘지 않는다.
3. **Given** 오늘(한국 시간 0시 기준) 이미 200장을 요청한 회원, **When** 한 장 더 요청하면, **Then** 하루 한도 초과(429)로 거부되고 "오늘은 사진을 200장까지 올릴 수 있어요. 내일 다시 시도해 주세요"가 보인다. 실패한 업로드도 1장으로 센다.
4. **Given** 회원, **When** 설정 화면을 열면, **Then** "사진 저장 공간 312MB / 1GB" 막대와 "지운 사진의 공간은 7일 뒤 돌아와요" 안내가 보인다.
5. **Given** 사용량이 90%를 넘은 회원, **When** 에디터를 열면, **Then** 사진 버튼 옆에 "남은 공간 약 100MB" 같은 안내가 보인다.
6. **Given** 사진이 든 글을 지운 회원, **When** 사용량을 확인하면, **Then** 정리 작업이 실제로 파일을 지울 때까지(연결 끊긴 지 7일) 사용량은 줄지 않는다.

### User Story 4 - 오프라인·업로드 실패에도 글이 사라지지 않는다 (Priority: P2)

네트워크가 끊기거나 업로드가 실패해도 작성자는 사진을 계속 본문에 넣을 수 있다. 사진은 기기 안에 보관되고 화면에는 정상으로 보이며, 연결되면 자동으로 다시 올라간다. 다만 아직 올라가지 않은 사진이 있으면 발행은 막힌다.

**Why this priority**: 사진 때문에 글이 유실되거나, 다른 사람이 볼 수 없는 주소가 공개 글에 들어가는 일을 막는다.

**Independent Test**: 오프라인 상태에서 사진을 넣고 자동 저장·발행을 시도한 뒤, 연결을 복구해 자동 재업로드와 주소 교체를 확인한다.

**Acceptance Scenarios**:

1. **Given** 오프라인 상태, **When** 사진을 넣으면, **Then** 사진은 기기에 보관되고 본문에는 업로드 대기 표시가 들어가며 화면에는 사진이 정상으로 보인다.
2. **Given** 업로드 대기 표시가 있는 본문, **When** 자동 저장이 일어나면, **Then** 자동 저장은 그대로 성공한다.
3. **Given** 업로드 대기 표시가 있는 본문, **When** 발행하면, **Then** 400으로 거부된다.
4. **Given** 연결이 돌아옴, **When** 자동 재시도가 성공하면, **Then** 대기 표시가 진짜 사진 주소로 바뀐다.

---

### User Story 5 - 대체글 권유와 GIF 재생 (Priority: P3)

작성자는 사진마다 대체글을 넣도록 권유받지만 강제되지는 않는다. GIF는 변환 없이 그대로 올라가고, 본문에서는 처음에 정지 장면과 ▶ 표시로 보이다가 누르면 움직인다.

**Why this priority**: 접근성과 데이터 절약을 위한 개선이며 핵심 업로드 흐름이 없어도 의미가 없다.

**Independent Test**: 대체글 없는 사진 2장이 든 글을 발행해 안내 후에도 발행되는지, 빈 대체글이 꾸밈 이미지로 표시되는지 확인하고, GIF가 든 글에서 정지 → 재생 → 정지 동작과 스크립트가 꺼진 환경의 원본 링크 동작을 브라우저 E2E로 확인한다.

**Acceptance Scenarios**:

1. **Given** 사진을 에디터에 넣음, **When** 본문을 보면, **Then** 대체글 자리는 비어 있고 원래 파일 이름은 들어가지 않는다.
2. **Given** 대체글이 빈 사진 2장이 든 글, **When** 발행 설정 창을 열면, **Then** "대체글이 없는 사진이 2장 있어요 [대체글 넣기]" 안내와 사진별 작은 미리보기·입력칸이 보이고, 입력하면 본문에 반영된다.
3. **Given** 대체글을 넣지 않음, **When** 발행하면, **Then** 발행은 막히지 않고 사진은 빈 대체글(화면 낭독기가 건너뛰는 꾸밈 이미지)로 표시된다.
4. **Given** 대체글이 125자를 넘음, **When** 입력하면, **Then** 거부하지 않고 안내만 한다.
5. **Given** GIF가 든 글, **When** 독자가 상세를 열면, **Then** 첫 장면 정지 이미지와 ▶ 표시가 보이고, 누르거나 키보드 Enter를 누르면 원본 GIF가 움직이며, 다시 누르면 정지 장면으로 돌아온다.
6. **Given** 스크립트가 꺼진 독자, **When** GIF 정지 이미지를 누르면, **Then** 원본 GIF가 새 탭에서 열린다.
7. **Given** 가로나 세로가 1920px을 넘는 GIF, **When** 고르면, **Then** 브라우저가 "GIF는 가로·세로 1920px까지 올릴 수 있어요"를 안내하고, 우회해도 서버가 완료 단계에서 거부하고 파일을 지운다.
8. **Given** 프레임이 300장을 넘는 GIF, **When** 완료를 알리면, **Then** 거부되고 파일이 지워진다.
9. **Given** 움직이는 WebP·APNG, **When** 올리면, **Then** 첫 장면만 남는다는 안내가 업로드 화면에 있고 첫 장면만 저장된다.

---

### Edge Cases

- 비공개 글의 사진도 주소를 알면 누구나 볼 수 있다(결정 사항). 주소는 추측할 수 없어야 하고, 저장소 목록 조회는 익명에게 막혀 있어야 이 전제가 성립한다.
- 서명을 위조하거나, 서명 뒤 경로를 바꾸거나, 서명과 다른 형식으로 올리거나, 5분이 지난 업로드 주소로 올리면 저장소가 거부해야 한다.
- 업로드 주소 없이(서명 없이) 익명으로 올리는 요청, 사진 경로 밖의 익명 읽기는 거부된다.
- 다른 출처(사이트)에서의 브라우저 직접 업로드는 거부된다.
- 남이 올린 사진을 내 글·프로필에 연결하려 하면 400으로 거부된다.
- 업로드만 하고 어디에도 쓰지 않은 사진은 24시간 뒤, 글에서 빠진 사진은 연결이 끊긴 지 7일 뒤 원본·썸네일 모두 자동으로 지워진다.
- 저장소 파일 삭제가 실패하면 기록을 남겨 두고 다음 정리 때 다시 시도한다.
- GIF는 원본을 고치지 않으므로 촬영 위치(EXIF)는 없지만 그 밖의 메타데이터는 남을 수 있다(알려진 한계).
- 썸네일이 없는 옛 사진은 목록 카드에 원본 주소를 쓴다.
- 프로필 이미지도 같은 업로드 흐름·저장 공간 합계·정리 규칙을 쓰지만, 이미지 규격(256×256)과 연결 규칙은 프로필 명세에서 정한다.

## Requirements *(mandatory)*

### Functional Requirements

**업로드 흐름**

- **FR-001**: 사진은 임시저장 흐름과 분리해 넣는 즉시 저장소로 MUST 업로드되어야 하며, 본문에는 사진 주소만 남아야 한다. (C-IMG-1)
- **FR-002**: 브라우저는 원본을 긴 변 최대 1920px·WebP 품질 0.8로 줄이고 EXIF(촬영 위치 포함)를 제거해야 MUST 하며, 가로 최대 640px·WebP 0.8 썸네일을 함께 만들어야 한다. GIF 원본은 변환하지 않고, 썸네일은 첫 장면으로 만든다. (C-IMG-1)
- **FR-003**: 시스템은 업로드 승인 요청에서 형식(jpg·png·gif·webp), 크기(10MB 이하), 요청 횟수, 저장 공간, 하루 장수를 MUST 검사한 뒤, 원본·썸네일 각각에 대해 5분 동안만 유효한 서명된 업로드 주소를 발급해야 한다. 승인 시점의 사진은 "임시" 상태로 기록된다. (C-IMG-1)
- **FR-004**: 사진 데이터는 서비스 서버를 거치지 않고 브라우저에서 저장소로 직접 MUST 올라가야 한다. (C-IMG-1)
- **FR-005**: 업로드 완료 시 시스템은 두 파일의 존재, 실제 크기(신고 크기 이하), 파일 앞부분의 실제 형식(확장자 위장 거부), 해상도(초대형 예: 1만 px 초과 거부), 썸네일 규격(가로 640px 이하·1MB 이하)을 MUST 다시 검사하고, 실패하면 저장소에서 파일을 지워야 한다. (C-IMG-1)
- **FR-006**: 저장 이름은 서버가 연·월 경로와 추측할 수 없는 고유 식별자로 MUST 만들어야 하며, 사용자의 원래 파일 이름은 경로·화면 어디에도 MUST NOT 쓰여야 한다(기록으로만 보관). 썸네일은 원본 이름에 `_thumb`을 붙인 규칙을 따른다. (C-IMG-1)
- **FR-007**: 사진 주소는 바뀌지 않으므로 1년 동안 변경 없는 캐시로 MUST 제공되어야 한다.
- **FR-008**: 업로드 요청은 사용자당 1분에 20장으로 MUST 제한되어야 한다.

**권한**

- **FR-009**: 비회원의 업로드 요청은 401, 이메일 인증 전 회원은 403(이유: 이메일 미인증)으로 MUST 거부되어야 한다. 인증된 회원과 관리자는 업로드할 수 있다. (C-AUTH-1, C-OWN-1)
- **FR-010**: 남이 올린 사진을 내 글이나 프로필에 연결하는 요청은 400으로 MUST 거부되어야 한다. (C-OWN-1)

**저장소 접근 규칙**

- **FR-011**: 저장소는 익명 사용자에게 사진 경로의 파일 하나 읽기만 MUST 허용해야 하고, 목록 조회·사진 경로 밖 읽기·서명 없는 쓰기는 MUST 거부해야 한다. (C-IMG-1)
- **FR-012**: 저장소는 서명 위조, 서명 뒤 경로 변경, 서명과 다른 콘텐츠 형식, 만료(5분 후) 업로드를 MUST 거부해야 한다.
- **FR-013**: 저장소는 우리 사이트 출처에서의 업로드(`Content-Type` 헤더만)만 MUST 허용하고 다른 출처는 거부해야 한다.
- **FR-014**: 저장소 접속에는 기본 관리자 계정이 아닌 앱 전용 키(올리기·읽기·지우기만)를 MUST 써야 하며, 비밀값은 환경 변수로만 주입한다. 저장소 관리 화면은 외부에 열지 않는다.
- **FR-015**: 서비스는 저장소의 접속 주소와 키만 바꿔 로컬 개발 저장소와 운영 저장소를 모두 MUST 쓸 수 있어야 하고, 저장소를 띄울 수 없는 환경을 위한 대체 저장 방식을 둔다.
- **FR-016**: 비공개 글의 사진도 주소를 알면 볼 수 있다(사진마다 권한 확인 없음). 이 규칙은 친구 공개가 공통에 들어오면 재검토한다.

**오프라인·실패**

- **FR-017**: 업로드가 실패하거나 오프라인이면 브라우저는 사진을 기기에 보관하고 본문에 업로드 대기 표시를 넣어 화면에는 정상으로 보여야 MUST 하며, 연결되면 자동 재시도해 성공 시 진짜 주소로 바꿔야 한다. (C-IMG-1, C-POST-2)
- **FR-018**: 업로드 대기 표시가 있어도 자동 저장은 MUST 성공해야 하고, 발행은 400으로 MUST 거부되어야 한다. (C-POST-3)

**글 연결과 정리**

- **FR-019**: 수동 저장·자동 저장 반영·발행 때 본문의 사진 주소를 뽑아 글과 사진의 연결을 MUST 갱신하고, 연결된 사진은 "연결됨" 상태로, 빠진 사진은 연결이 끊긴 시각을 기록해야 한다. (C-IMG-1)
- **FR-020**: 발행 때 본문의 첫 번째 업로드 사진의 썸네일 주소를 글의 카드 썸네일로 MUST 지정해야 한다. 상세·링크 미리보기에는 원본을 쓴다. (C-READ-1)
- **FR-021**: 매일 정리 작업은 "임시" 상태로 24시간이 지난 사진과 연결이 끊긴 지 7일이 지난 사진의 원본·썸네일 파일을 저장소에서 지운 뒤 기록을 MUST 지워야 한다. 저장소 삭제는 데이터 저장 처리 밖에서 하고, 실패하면 다음 정리 때 다시 시도한다.
- **FR-022**: 프로필 용도 사진은 용도로 구분되어 같은 정리 규칙을 따르며, 프로필로 연결된 동안은 MUST 지워지지 않아야 한다.

**저장 공간 한도**

- **FR-023**: 회원마다 저장 공간 1GB와 하루 200장(한국 시간 0시 기준) 한도가 MUST 있어야 한다. 사용량은 그 회원이 올린 모든 사진(임시·연결됨·정리 대기, 프로필 포함)의 원본 + 썸네일 크기 합계다.
- **FR-024**: 업로드 승인 시 "지금 사용량 + 이번에 올릴 크기(원본 + 썸네일)"가 1GB를 넘으면 저장 공간 초과(409)로, 하루 200장을 넘으면 하루 한도 초과(429)로 MUST 거부해야 한다. 실패한 업로드도 하루 장수에 센다.
- **FR-025**: 같은 회원의 업로드 승인이 동시에 여러 건 들어와도 허용된 합계가 1GB를 MUST NOT 넘어야 한다.
- **FR-026**: 지운 사진의 공간은 정리 작업이 파일을 실제로 지울 때 돌아와야 MUST 하며, 글을 지워도 바로 돌아오지 않는다.
- **FR-027**: 회원은 설정 화면에서 사용량·한도·오늘 업로드 수를 MUST 볼 수 있어야 하고, 에디터는 한도 초과·하루 한도·90% 초과 시 정해진 안내 문구를 보여야 한다.

**대체글**

- **FR-028**: 에디터는 사진을 넣을 때 대체글 자리를 비워 두고 원래 파일 이름을 MUST NOT 넣어야 한다.
- **FR-029**: 발행 설정 창은 대체글이 빈 사진 수를 안내하고 사진별 입력칸을 제공해야 MUST 하며, 입력한 대체글은 본문에 반영된다. 대체글이 없어도 발행은 MUST NOT 막혀야 한다.
- **FR-030**: 빈 대체글은 "빈 대체글"(꾸밈 이미지)로 MUST 그려져야 하며 대체글 속성 자체를 빼서는 안 된다. 125자를 넘으면 안내만 한다.

**GIF**

- **FR-031**: GIF는 압축·크기 조정·변환 없이 MUST 올라가야 하며, 10MB 이하, 가로·세로 각 1920px 이하, 프레임 300장 이하여야 한다. 서버는 완료 단계에서 해상도·프레임 수를 파일 전체를 해석하지 않고 다시 확인해 넘으면 거부·삭제한다.
- **FR-032**: 본문의 우리 저장소 GIF는 첫 장면 정지 이미지(썸네일) + ▶ 표시로 MUST 보이고, 누르거나 Enter를 누르면 원본이 재생되며 다시 누르면 정지해야 한다. 스크립트가 없으면 정지 이미지를 눌러 원본이 새 탭에서 열린다. 이 표시는 본문 정화 허용 목록과 브라우저 보안 정책(인라인 스크립트 금지)을 바꾸지 않고 이뤄져야 한다.
- **FR-033**: 움직이는 WebP·APNG는 첫 장면만 남는다는 사실을 업로드 화면에 MUST 안내해야 한다.

### Key Entities *(include if feature involves data)*

- **사진(Image)**: 올린 회원, 용도(글 / 프로필), 상태(임시 / 연결됨), 저장 이름(원본·썸네일), 원래 파일 이름(기록용, 비노출), 형식, 원본 크기·썸네일 크기, 가로·세로 해상도, 연결이 끊긴 시각, 만든 시각.
- **글-사진 연결(Post Image)**: 글과 사진의 다대다 연결. 정리 작업과 카드 썸네일 지정에 쓰인다.
- **글의 카드 썸네일**: 본문 첫 업로드 사진의 썸네일 주소. 발행 때 지정.
- **저장 공간 사용량**: 회원별 사진 원본 + 썸네일 크기 합계(따로 저장하지 않고 합계로 계산), 하루 업로드 장수.
- **업로드 승인**: 사진 한 장에 대해 원본·썸네일 업로드 주소 2개와 5분 유효 기간.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 일반 휴대폰 사진(약 5MB)이 업로드 전 약 10분의 1(300~500KB)로 줄고, 업로드된 원본에서 촬영 위치 정보가 100% 제거된다.
- **SC-002**: 형식 위장·10MB 초과·해상도 초과·썸네일 규격 위반 파일의 100%가 거부되고 저장소에 남지 않는다.
- **SC-003**: 저장소 검증 항목(정상 업로드 성공, 서명 위조·경로 변경·형식 불일치·만료 거부, 익명 목록 거부, 익명 파일 읽기 성공, 서명 없는 익명 쓰기 거부, 사진 경로 밖 익명 읽기 거부, 우리 출처 허용·다른 출처 거부) 11가지를 고정한 저장소 버전에서 모두 통과한다.
- **SC-004**: 한도 직전에서 동시 업로드 승인 10건을 보내도 허용 합계가 1GB를 넘는 경우가 0건이다.
- **SC-005**: 9장짜리 목록 카드의 썸네일 전송량이 약 0.4MB 수준이다(원본 사용 시 약 3.6MB 대비).
- **SC-006**: 업로드 대기 사진이 든 글의 발행 시도 100%가 거부되고, 같은 상태의 자동 저장은 100% 성공한다.
- **SC-007**: 대체글이 없는 사진이 든 글도 100% 발행되며, 원래 파일 이름이 화면·주소에 나타나는 경우가 0건이다.
- **SC-008**: 정리 작업 후 "임시" 24시간 초과·연결 끊김 7일 초과 사진이 저장소에 남아 있는 경우가 0건이다.

## Assumptions

- **Tier**: C-IMG-1은 Tier B(공통 포함 권장).
- **결정 기록에서 가져온 사항**: 사진은 임시저장과 분리해 즉시 업로드·본문에는 주소만, 버려진 사진은 배치 정리(2026-10-02), 비공개 글 사진은 주소를 알면 보임(2026-10-02 Q10), 서명된 업로드 주소 방식(2026-10-02), 640px 썸네일(2026-10-02), **파일 저장소는 MinIO(S3 API, 서명 방식 SigV4) — 운영은 NHN 제공 MinIO, 로컬은 커뮤니티 포크 이미지 버전 고정(2026-10-06)**.
- **문서 간 충돌 처리**: docs/23-image.md I-1은 RustFS `1.0.1`을 제안했고 docs/04 이전 판은 SeaweedFS를 제안했으나, 결정 기록 2026-10-06의 MinIO 결정을 따른다. 23 §2-3의 저장소 검증 항목(원래 RustFS 대상)은 고정한 MinIO 포크 이미지 기준으로 적용하며, 04 §6-1이 4가지를 더해 11가지가 되었다.
- **23 문서의 결정(용량 1GB·하루 200장, 대체글 권유, GIF 규칙)**은 공통 결정 기록 표에는 없지만 23 문서의 결정 기록 추가분(2026-10-04)으로 확정된 것으로 보고 적용했다.
- **설정값**: 저장 공간 1GB, 하루 200장, 1분 20장, 업로드 주소 유효 5분, 원본 1920px·썸네일 640px·품질 0.8, 정리 기준(임시 24시간·연결 끊김 7일), GIF 1920px·300프레임은 설정값으로 둔다.
- **운영 배포 전 확인(NHN MinIO)**: path-style 접속 지원, 앱 전용 키 발급, 버킷 정책·CORS 설정 권한, 사진 공개 주소(저장소 또는 CDN). 같은 검증을 운영 접속 주소로 다시 실행한다.
- **보안 정책 의존성**: 브라우저가 저장소로 직접 올리고 사진을 표시하려면 본문 정화 명세(007)의 브라우저 보안 정책에 저장소 주소가 연결 허용·이미지 허용으로 포함되어야 한다(04 §6-1). 007이 인용한 12 §8 정책에는 연결 허용 항목이 없어 계획 단계에서 맞춰야 한다.
- **범위 밖**: 임시저장·자동 저장·충돌 처리(04 §2)는 임시저장 명세, 프로필 이미지 규격·소셜 사진 복사는 프로필 명세(11), 카드 표시는 목록 명세(009), GIF 재생 스크립트를 상세 페이지에 넣는 것은 상세 명세(010)에서 다룬다. 저장소 데이터 백업 주기는 배포 담당(공통 범위 밖)이다.
